# CLAUDE.md

Guidance for Claude Code in this repo. **Keep this file at ~65 lines** — to add something, cut something. Record traps and decisions, not what the code already says plainly.

## Naming

The UI name is **ArchiLog**; the npm package, the folder (`work-journal`), the GitHub repo (`-`) and the Vercel project (`-`) keep the old name **on purpose** — don't "fix" them for consistency.
**할 일 belongs to `work_logs.next_action` alone.** `schedule_items` are 일정, `project_checklist_items` are 항목 (체크리스트 collectively). All three were once called 할 일 and `등록된 할 일이 없어요` appeared on two unrelated screens — don't merge them back.
현장 vs 프로젝트 is still mixed (checklist picker, the 현장 없음 option on 일정). Ask before sweeping it.

## Architecture

`npm run dev` (Turbopack, :3000) · `npm run build` · `npm run lint` · `npx tsc --noEmit` (there is no `typecheck` script). **No test suite exists** — verification is those last three. Env lives in `.env.local` and hot-reloads.

Next.js 16 App Router + React 19 + TS + Tailwind on Supabase (PostgREST, no ORM, no client-state library). Mutations are Server Actions in `actions.ts`/`*-actions.ts` beside their routes. Every table is RLS'd to `auth.uid() = user_id` and there is no `service_role` key anywhere, so queries filter by `user_id` and let RLS do the rest. Schema in `supabase/schema.sql` + `migration_0NN_*.sql`; TS shapes in `src/types/`.

## Domain traps

- **`work_logs.status` is not progress — it records what happens next:** `todo` (`next_action` + optional `next_action_date`), `waiting` (`result`, shown as **코멘트**), `done` (`decision` + optional `decision_dates`). **`result` is not a general 결과 field any more** — the form-wide 결과 textarea was removed and its column reused for the waiting comment, so it is written only from the `waiting` branch of `StatusFieldset`. Each field is written only for its own status and `createLog` nulls the others, but `updateLog` **leaves `result` untouched outside `waiting`** so legacy 결과 text on todo/done logs isn't destroyed unseen; readers still print it (labelled 코멘트).
- **`updateLogStatus` (the badge cycle) deliberately does NOT clear those fields**, so one stray click can't destroy typed text and cycling back restores it. Every reader gates on status, so a stale value never shows.
- **`closeLog(id, decision, decisionDates)` omits empty fields rather than nulling them**, so earlier values survive — which means **clearing them is only possible from the edit form**. `DecisionDatesField` emits **one hidden input per row carrying that row's JSON**; parallel `getAll()` arrays would pair date to content by position and break the moment one side is empty.
- **`next_action_date` ≠ `decision_dates`.** One is "the day I must act", the other "the day(s) this was agreed for" — a closed log still owns calendar slots. Never merge them.
- **`decision_dates` is `jsonb`** `[{date, time, content}]`, because a multi-day 협의 differs per day. Read it **only** through `parseDecisionDates()`: it drops malformed rows, keeps one entry per date, and sorts. Uniqueness is load-bearing — N dates become N `CalendarEntry` rows **sharing one `id`**, safe only because React keys are scoped per day. jsonb cannot be date-range filtered, so both calendars fetch `.not("decision_dates","is",null)` and pick in-range dates in JS; fine at this size, but past a few thousand closed logs give the pairs their own table rather than adding a parallel `date[]`.
- **Times are optional and sit beside their date:** `schedule_items.start_time`, `work_logs.next_action_time`, and a `time` per `decision_dates` entry. Timeless means 하루 종일 and **sorts last** (`compareTimes()`); read through `formatTime()` because Postgres returns `HH:MM:SS` while `<input type="time">` speaks `HH:MM`. `updateNextAction` drops the time when the date is cleared. A log's own `date` has no time — it means "written that day", not an appointment.
- `categories` is a text array; `category_details` (jsonb) holds the sub-tags plus a `{seq, title}` per numbered category. **협의 numbering is opt-in** — a `CONSULT_NUMBERED_FIELD` checkbox, off for every new log, because most 협의 are 자잘한 것 and numbering them made 회차 meaningless (PT/브랜딩 are still always numbered). So `seq` must be **`max(existing seq)+1`, never `count+1`**: counting tagged rows lets unnumbered 협의 eat numbers. Editing an already-numbered log keeps its `seq`. `log_type` picks the DESIGN or BUILD category set; old logs keep tags no longer offered as checkboxes.
- `projects.phase` feeds `PHASES_BY_TYPE`, which drives the DESIGN/BUILD split app-wide. 건폐율/용적률 are **derived on every render**, never stored, so they can't go stale.
- Checklist `group_id` is nullable with `on delete set null`, so deleting a folder unfiles its items instead of destroying them. `assignee` still stores the "나" sentinel (`ME_ASSIGNEE`); the edit form posts `prev_assignee` so switching away doesn't wipe a legacy name the form never displayed. `ProjectChecklist`'s props all default to the original flat-list behaviour — check every call site before changing a default.
- A log's 할 일 is deliberately **not** wired to checklist items. `StatusFieldset` is shared by `JournalForm`/`EditLogForm` and its radios are controlled, so `JournalForm` remounts it via `key={state.submittedAt}` — `form.reset()` alone won't clear them.

## Screens

Drill-down state lives in **search params, not React state** (`?project=&group=`, `?month=`, `?week=`, `?date=`), so back/forward and link sharing work; unknown ids fall back to the parent screen instead of erroring.
- **`/dashboard`** — 일정 + entry form + today's logs. `TodayEntry` owns the entry date (지난날 기록하기) and passes it as a hidden field, so **never `key={date}` the form** — it would wipe what was already typed. `TodayEntry` keeps a local `PHASES_BY_TYPE` missing `supervision`; known, left alone on request.
- **`/weekly`** — read-only, groups todo/waiting logs and undone 일정 **by project** into 밀린 것 / 이번 주 / 답변 대기 / 날짜 없음. The undated buckets are the whole point (they appear on no calendar) and are **current-week-only**, or the same pile would repeat in every week. It stays read-only: rows are links out to where the thing is actually editable (`editHref()` — 일지 → `/journal?project=`, 일정 → `/calendar?date=`), never an edit form here.
- **`/journal`** — filterable list with `OpenLogsSection` on top, derived from the already-fetched logs so it narrows with the active filters at no extra round-trip.
- **`/calendar`** — 일정 + dated 할 일 + in-range 협의된 날짜 as one `CalendarEntry` union (`src/types/calendar.ts`, kept out of the components so server page and client files can import it without a cycle). Cells are buttons; `CalendarDayPanel` expands a day and is remounted with `key={selected}` so per-row edit state can't leak between days. `?date=` seeds `selected` (and picks the month when `?month=` is absent) so other screens can link straight to an editable day; a date outside the grid is ignored rather than opening an empty panel. Only 일정 can be *created* here — a 할 일 exists only inside a log.
- **`/projects`** — cards are **not one link any more**: the 일지 status badges go to `/journal?project=`, each checklist folder row to `/checklist?project=&group=` (`UNGROUPED_PARAM` sits in `src/types/project.ts` so both builders agree). Card-wide clicking survives as the title link's `after:absolute after:inset-0` overlay, so **any link added inside a card needs `relative`** or the overlay eats it, and nothing above the overlay may set `overflow-hidden`.
- **`/checklist`** — 프로젝트 → 폴더 → 항목. A project with no folders skips the folder screen, **so the 폴더 추가 form must also render on the flat list** or no first folder could ever be created. Checklist items are managed only here, never on the project page.
- **`/projects/[id]`** — `ProjectCalendar` first, then info card / 진행사항 / 협력업체 / 문서함. It is the only view combining 기록 (by `date`), 할 일 (by `next_action_date`), 협의된 날짜 and 일정; anything already filed on a day is not filed there twice. Chips are coloured **by kind** (`CHIP_CLASS`) since every row is the same project; a numbered 안건 is a *filled* brand chip rather than a new hue, because amber/violet/emerald/red already mean 할 일/답변 대기/종료/지남 elsewhere. Chip text is **never the log body** — it truncates to nothing useful. `logChipLabel()` gives `협의-02: 제목`, else the badge string (`검토(법적근거) · 설계(CAD)`), and `isNumberedAgenda()` must keep reading the *same* helper or the colour and the text disagree. Chips carry **time + that label only** and are flattened into one list before `MAX_CHIPS` — slicing per kind would put nine rows in a 96px cell. The calendar heading carries the project name because the page's only `<h1>` now sits below it. `ScheduleRow` (exported from `CalendarDayPanel`) must be handed `projects={[this project]}`, or saving silently unlinks the 일정, and the 답변 대기 pill is **shown regardless of the month on screen** because a waiting log sits on its own record date and would otherwise vanish into a past month.
- Every action in `schedule-actions.ts` must revalidate `/projects/<id>` via `revalidateAll()`; `updateScheduleItem` reads the old `project_id` first so moving a 일정 refreshes both projects.

## Colours

Palettes are **complete class strings** — Tailwind cannot see names assembled at runtime.
- `projectColorClass()`/`projectBarClass()` hash the project id into a fixed 10-colour palette (derived, not stored). **Reordering it silently recolours every existing project.** Accents are `border-l-*`, not `border-*`, or they fight the box's grey border on the other three sides.
- `STATUS_BADGE_CLASS` (log status) and `CHECKLIST_STATUS_BADGE_CLASS` — the latter is applied to a `<select>`, so **keep its text dark** or the expanded option list goes invisible in some browsers.
- `dueBadge()` (`src/lib/date.ts`) owns 지남/오늘/D-N so `/journal` and `/weekly` can't drift apart. Every date helper is `Date.UTC`-based to avoid timezone drift.
- **`tailwind.config.ts` content is a single `./src/**/*.{ts,tsx}` glob on purpose.** Listing folders individually once purged every colour constant in `src/types/*.ts`: the class names were in the markup but no CSS rule was emitted, so edits appeared to do nothing. Don't narrow it back.

## Auth, files, deploy

Supabase Auth via `@supabase/ssr`; session refresh and route protection live in **`src/proxy.ts`** (Next 16 renamed `middleware.ts`), delegating to `updateSession()`.
Attachments go to **Dropbox, not Supabase Storage** (`src/lib/dropbox/client.ts`, raw fetch). `Dropbox-API-Arg` is ASCII-only, so non-ASCII filenames must be `\uXXXX`-escaped (`encodeApiArg()`); a refresh token only carries the scopes enabled when it was issued, so new scopes need a fresh OAuth run; `next.config.mjs` raises the 1MB Server Action body limit for photos.

**Push to `master` auto-deploys** to the Vercel project `-` (alias `one-chi-60.vercel.app`), which is *not* named after the folder — `vercel link` without `--project -` creates a wrong one. Env vars must exist in all three Vercel environments.
**Deploying does not run migrations.** After adding `supabase/migration_0NN_*.sql` the **user must paste it into the Supabase SQL Editor and run it** — always say so explicitly in the completion summary. Missed-migration symptom: `Could not find the '<column>' column ... in the schema cache`; if the column does exist the cache is stale (`notify pgrst, 'reload schema';`). `add column if not exists` is re-runnable but **`create policy` is not**, and `if not exists` **skips on a type mismatch** — that silently left `decision_dates` as `date[]` once. Latest: `017` decision_dates (jsonb), `018` times.

## Working across machines

The repo sits inside Dropbox, but `.git`, `node_modules` and `.next` are excluded per machine via the `com.dropbox.ignored` NTFS attribute. **The attribute lives on the directory, so deleting `.next` throws it away** and the dev server then fails with `EPERM ... .next/dev/...manifest.json.tmp` or a Turbopack panic. Re-apply with `Set-Content -LiteralPath 'C:\abs\path\work-journal\.next:com.dropbox.ignored' -Value 1` — the path must be **absolute**, or a relative one reads `node_modules:` as a drive letter and reports it missing when it isn't. Deleting `.next` may also half-fail while Dropbox holds handles on subdirectories; the dev server rebuilds whatever is missing, so let it.
The same `EPERM` appears when two dev servers overlap **or when `npm run build` runs while dev is live** — both write `.next`, and dev then 500s every route until restarted, so stop dev before building and check for a stale `next dev` before blaming Dropbox. **git push/pull is the real sync between machines**, not Dropbox: commit and push before switching, pull before starting, and regenerate `node_modules` per machine.
